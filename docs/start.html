Before you start

Work in your application's repository, not this one. Check the participant requirements, use an approved workspace, and know who can approve access and architecture.

Working with an existing application?

Open its repository, and tell the creator where any architecture or operating records live if they're stored elsewhere. Bring:

  • The current user journey and the one thing you want to add.
  • Existing API contracts and data sources, with their owners and access limits.
  • What must not change, including authorization.
  • Deployment constraints, regression checks, and who owns rollback.

Use synthetic inputs until you've agreed access to customer data. Say how the application should behave when AI is unavailable or the evidence isn't enough. Missing documentation doesn't mean a control or service doesn't exist.

Reuse what already works. Replace something only for a clear reason, with a migration plan that keeps it compatible.

Set up your workspace

Run commands from your application directory unless a step says otherwise. If a command fails, read the error and check for partial files before retrying.

Install the plugin

For GitHub Copilot CLI:

copilot plugin marketplace add microsoft/frontier-agentic-cobuild-rvas
copilot plugin install agentic-cobuild@agentic-cobuild
copilot plugin list

For VS Code, add the marketplace without replacing existing entries:

{
  "chat.plugins.enabled": true,
  "chat.plugins.marketplaces": [
    "microsoft/frontier-agentic-cobuild-rvas"
  ]
}

Open Extensions, search for @agentPlugins, install Agentic Co-build, and enable it for the application workspace.

Check the workspace

In CLI, use /skills and /mcp. In VS Code, use Chat: Configure Skills and the MCP server list.

You should see AI Agent Creator, Idea Forge, Cloud Architecture Diagram, Diagram Design, Wireframer, Cost Estimation, Grilling, Domain Modeling, Wait What, and the Microsoft Learn MCP server. If something is missing, reload your host and reinstall the plugin.

Use Claude Opus 5.5 for the whole AI Agent Creator session, including the optional wireframe, and for implementation. In VS Code, pick it in the model picker. In Copilot CLI, run:

/model claude-opus-5.5

Describe what you want to build

If the business context is spread across several people, run the discovery session guide first, and get approval before recording or processing the discussion.

Select AI Agent Creator from your host's skill picker or slash completion, then adapt one of these prompts.

AI Agent Creator prompts

For a new application:

/agentic-cobuild:ai-agent-creator Build a demo based on the 2025 Monza Grand Prix,
using real OpenF1 data. The goal is to show how to combine race data and
business knowledge to support a strategic decision: pit or stay out.

For an existing application (for example, extending the race demo):

/agentic-cobuild:ai-agent-creator Add a what-if comparison to the existing Monza
race demo. Let users adjust pit-stop time loss and expected tyre pace, compare
pit versus stay-out scenarios, and see which assumptions change the recommendation.
Distinguish observed OpenF1 data from hypothetical inputs. Inspect the current
stack, preserve established interfaces, and account for existing data-access
and deployment constraints.

Your first milestone is confirmed discovery. Answer the creator's questions. When you agree on the outcome, the first user journey, and the architecture decisions, confirm discovery. The creator then prepares the architecture package.

Work in the shared canvas

In the GitHub Copilot app, you can follow the session on a shared screen. Ask:

Open the Customer workspace canvas.

The canvas lists the architecture package and shows each file as the creator writes it: Markdown, the HTML diagrams, and the .drawio pages. The creator points it at the file to review next, and it shows the current phase. The canvas is read-only. You still confirm and approve in the chat.

Canvases are experimental, and the plugin works the same without one. If you don't see it, update the plugin and turn on experimental features.

Review what the creator understood

Before you confirm discovery, the creator shows what it understood, as diagrams and text:

  • a swimlane of the first journey, showing which steps belong to the user, the AI, fixed system logic, approvers, and external systems;
  • a map of the agreed domain terms, if there are enough to relate;
  • the lifecycle of a business object that waits, needs approval, or retries;
  • scenarios for success, ambiguous input, a rejected action, and a failed dependency.

It saves the Mermaid source in docs/architecture/visuals/shared-understanding.md and renders each view as HTML beside it with diagram-design. Open the HTML files in a browser from either host. In VS Code 1.109 or later, enable the Render Mermaid Diagram chat tool to see the diagrams inline as well. Correct anything that looks wrong. Changing a diagram changes the record. The confirmed scenarios become acceptance criteria in the specification and clickable paths in the optional prototype.

The creator writes the editable diagrams, architecture, specification, implementation plan, and cost estimate under docs/architecture/. Review the diagrams, and have someone else review the whole package before you approve it. If you can't do either, say so and record the exception.

Optional final wireframe

After all five architecture files are complete and reconciled, the creator explicitly asks whether you want a clickable, low-fidelity prototype. Answer in the same session. If you say yes, it uses the bundled wireframer skill to illustrate the confirmed journey under docs/architecture/prototype/, with synthetic data and simulated actions. If you say no, the architecture package remains complete.

The prototype isn't a production implementation and doesn't connect to live systems. Review it with the architecture package.

Approval ends this workflow. The optional prototype does not authorize delivery. Start implementation separately. Approval doesn't change your code, generate infrastructure, or provision resources.

Start implementation in a new session

Pick one workflow and don't mix them. Each treats the approved files under docs/architecture/ as the source of truth.

Workflow Choose it when Entry point
Direct from the documents You want the shortest path from an approved package to working code Direct prompt
Matt Pocock spec and tickets You want a local spec, dependency-linked tickets, and bounded parallel delivery /to-spec, /to-tickets, then /implement-spec
Spec Kit You want a constitution, feature spec, plan, and task artifacts before coding Spec Kit's specify, plan, tasks, and implement commands

Direct from the documents

Open a new session and attach the whole docs/architecture/ folder. Use this path unless you need the extra coordination of the other two.

Read everything in @docs/architecture/, including the specification,
implementation plan, solution document and diagram, and cost estimate.
Implement the approved plan in dependency order. Treat the specification and
its acceptance criteria as the requirements source of truth. Follow the
approved architecture, preserve existing interfaces and authorization, and
add focused tests for changed behavior. Run the relevant checks and report
actual results. Do not change an architecture decision without approval.
Do not commit, provision, deploy, or change production data.

Matt Pocock spec and tickets

Use this for independent work items that need dependency tracking. If /to-spec, /to-tickets, and /implement-spec aren't available, install the Matt Pocock engineering workflow. Tickets live in local Markdown, not remote issues.

/to-spec Convert the approved docs/architecture/ package into one bounded local
implementation spec. Preserve its requirement and acceptance IDs, architecture
decisions, interfaces, authorization, cost constraints, and out-of-scope work.
Do not implement yet.

/to-tickets Break the local spec into dependency-linked, testable tickets.
Keep every ticket linked to the original acceptance criteria. Show the proposed
breakdown before writing it. Do not publish remote issues or implement yet.

Open a new session for delivery:

/implement-spec Implement the approved local spec and tickets. Reconcile them
with the current source and the full docs/architecture/ package. Preserve the
approved architecture and existing contracts. Run focused and combined checks.
Do not push, open a pull request, provision, deploy, or change production data.

Spec Kit

Set up Spec Kit, then run its constitution, specify, clarify (if needed), plan, and tasks commands against the approved docs/architecture/ package. Don't let them overturn decisions that are already settled.

Open a new session after the feature plan and tasks are reviewed:

/speckit-implement Implement only the reviewed feature tasks. Treat the
docs/architecture/ package and its acceptance criteria as authoritative.
Preserve the approved architecture, interfaces, authorization, and cost
constraints. Run the documented tests and record actual results. Do not commit,
provision, deploy, or change production data.

Run /speckit-converge after each implementation pass, and repeat until the feature converges or you've recorded what's blocking it.

Whichever workflow you use, get approval before changing an architecture decision.

Once targeted checks pass, run the implementation and security reviews, fix what they find, and rerun the affected tests. If the review tools aren't available, ask a person to review and note that.

The operating team still owns production acceptance and rollback.

Command and prompt reference

Use these after implementation, or to maintain an existing setup.

Review prompts

Implementation review:

/review Review the staged and unstaged implementation against
@docs/architecture/specification.md,
@docs/architecture/implementation-plan.md, and
@docs/architecture/solution.md. Identify unmet or partially met acceptance
criteria, skipped or out-of-order plan steps, architecture deviations,
regressions, and missing tests. Rank findings by severity and include file and
line references.

Security review:

/security-review Analyze the staged and unstaged implementation for exploitable
security vulnerabilities, insecure defaults, authorization or data-isolation
failures, secret exposure, injection risks, unsafe external interactions, and
dependency or configuration weaknesses. Rank findings by severity and confidence,
include file and line references, and recommend the smallest safe fix for each
finding.
